Observability is the first half of Belvedir; the second half is closing the loop. Every project can run one or more **improvement loops** over the same production traces. **Harness evolution** and **Prompt evolution** rewrite what your agent runs and reads. **LoRA finetuning** distills your best traffic into a small model's weights. All of them end back in production, producing better traces.

```
             ┌──────────────────────────────────────────┐
             │                  deploy                  │
             ▼                                          │
  your agent in production                              │
             │  every LLM + tool call (the belvedir SDK)│
             ▼                                          │
  traces ──► sessions ──► tasks ──► task groups         │
                            │                           │
             what went wrong│what went right            │
             ┌──────────────┴──────────────┐            │
             ▼                             ▼            │
  Harness evolution /           LoRA finetuning         │
  Prompt evolution              (distill your best      │
  (rewrites prompts, skills,    tasks into a small      │
  memory, code)                 model's weights)        │
             │                             │            │
             ▼                             ▼            │
  GitHub PR, gated on           fine-tuned model,       │
  your review                   graded by benchmarks    │
             │                             │            │
             └──────────────┬──────────────┘            │
                            └───────────────────────────┘
```

## Types of training

Each loop improves a different layer of your agent against its own production traces:

- **Prompt evolution** improves what your agent is told and remembers (system prompts, skills, instructions, memory files), never its application logic. Production sessions show what it misses and should have remembered; the loop distills that back into the scaffolding.
- **Harness evolution** is the same loop with the whole harness on the table: prompts, tools, and code improve together, and the winner opens a PR.
- **LoRA finetuning** trains lightweight LoRA adapters on your traces on top of a supported open base model: cheap to run, quick to iterate, and swappable per task type. See [LoRA finetuning](/training/overview).

Loops are configured per project from **Training → Loops → Make a loop**, and a project can run several at once. Each loop you make takes a name of your own in the wizard.

## Harness evolution and prompt evolution

Both loops start from your repo exactly as it is today. Each example is one real trace: what your agent actually did, plus its outcome. The difference between the two loops is what may be touched. Harness evolution can edit the whole repo. Prompt evolution is limited to scaffolding (prompts, skills, memory files, instructions), so it improves what the agent is told and remembers, never its application logic.

Belvedir scores candidates against your recorded traces; your agent is not run against live users. Every proposed change cites the traces that motivated it.

### Two designs

Each project picks a **design**, the method that proposes changes. Pick it in the setup wizard's **Choose your approach** step, or with `belvedir setup <project> --design loop1|loop2`.

- **Loop 2 (diagnose and repair)**, the default. It triages failing traces into failure modes, diagnoses each root cause against your repository, and writes targeted fixes. Good when failures cluster into a few identifiable causes you want fixed precisely.
- **Loop 1 (GEPA)**, the original design. It evolves candidates with [GEPA](https://arxiv.org/abs/2507.19457)'s evolutionary search. Good for open-ended improvement when you would rather explore many variants than fix named failures.

### Review before anything ships

By default nothing ships without you: proposals wait as per-file diffs under **Training → History**, and approving one opens the GitHub PR. Autonomy is set per loop in the setup wizard: **Review first** (the default) or **Auto-PR** to skip the gate.

## Failure signals

What counts as a failing trace is a per-project choice of **optimization signals**: **Errors** (traces with failed LLM or tool calls), **Latency** (traces slower than 5 seconds end to end), and **User frustration** (users repeating themselves or correcting the agent). The setup wizard suggests signals from your improvement-target text; runs focus on traces matching the signals you select.

## Repository access

To read your repo and open PRs, a loop needs GitHub access. Connect the **Belvedir GitHub App** from your account page; you choose exactly which repositories the app may touch on GitHub's own grant screen. Then, in **Project settings → Repository access**, pick the repos this project's loops may use from your connected accounts. Adding a repo is verified against your own GitHub access, and from then on it works for everyone on the project: teammates run loops and approve PRs through Belvedir without ever holding repo credentials (repository access is scoped to each run; nothing is stored). Revoke at any time by uninstalling the app or narrowing its repo selection on GitHub. The **Harness access** permission under **Project Permissions** turns repository access off for the whole project; see [Data handling](/data-handling).

## One skeleton

Every loop shares one skeleton: propose a variant, score it against reality, keep the winner. Optimization loops propose text scored against past traces; LoRA finetuning proposes weights scored by benchmark runs. [Auto-training](/training/overview#auto-training) can keep the LoRA loop turning on its own.
