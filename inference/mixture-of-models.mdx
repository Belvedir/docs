Agents don't need one model for everything. A small model handles cheap, high-volume steps and a bigger one handles hard reasoning; the question is who decides. You can decide in your own code, or let a Belvedir router decide per call. This page is the home for how routers work; to send your calls through one, start with [Route your calls](/inference/route-your-calls).

## Routing in your own code

Both clients below are instances of the same OpenAI class, so a single `instrumentModules: { openAI: openai.OpenAI }` traces them all:

```ts
import OpenAI from "openai";

const local = new OpenAI({
  baseURL: "http://127.0.0.1:8080/v1", // Belvedir Local, see Local Models
  apiKey: "local",
});
const hosted = new OpenAI({
  baseURL: "https://platform.belvedir.ai/api/v1/route",
  apiKey: process.env.BELVEDIR_API_KEY,
});

// route each step to the model that fits it
const { client, model } = needsDeepReasoning(step)
  ? { client: hosted, model: "anthropic/claude-sonnet-5" }
  : { client: local, model: "qwen3:4b" };

const res = await client.chat.completions.create({ model, messages });
```

You can write `needsDeepReasoning` yourself, or ask Belvedir: [`POST /api/v1/route`](/api-reference/route) returns the model a router would pick without executing anything, so your code can run local models and your own provider accounts against the same decision.

## Routers

Routing is configured on the **Routers** page. A router holds three size tiers plus per-task-group assignments:

- **Big**: serves clearly hard requests.
- **Medium**: the default; serves the bulk.
- **Small** (optional): serves quick machine tasks, such as a short single-shot instruction with a clear task shape and no code.

The cheaper tiers only ever serve machine-shaped tasks: calls that classify, extract, summarize, or demand a strict output format, template-style prompts, and tool loops. When a person is talking to the model (a dialogue, or a message with no task markers) the response comes from the top of the router; ambiguous requests count as conversation, so they route up, not down. Complexity is scored on the instruction itself: pasted documents and payload text never escalate a request on size alone, though pasted code still counts as hard.

A project can hold several routers:

- Exactly one is the **auto** router. It serves calls that say `model: "auto"` or name no model. The others are drafts: stage a new setup there and click **Make auto** to switch, instantly and reversibly. The auto router cannot be deleted, only replaced.
- The first inference call that names a real model creates a router **anchored** on that model, listed as "From your code" and editable like any other. The anchored model is the router's ceiling and answers every conversational call; its Medium and Small tiers take only the machine-shaped tasks underneath. Deleting one means the next call naming that model recreates it.

Every new project starts with a Default router: GLM 5.2 serves the bulk (Medium), clearly hard requests escalate to Claude Fable 5 (Big), and quick machine tasks take Qwen 3.5 9B (Small). A project created with **Chinese models** off gets Grok 4.6 as Medium and Llama 3.2 3B as Small instead. The decision is fast and replayable: no LLM sits in the decision path, and the same input decides the same way.

## Task groups

Each request is matched to your project's [task groups](/how-it-works). A task group you assigned a model to serves that model (tier `group`); task groups with no assignment fall to the tier defaults above. Pass your session id with each call and a conversation stays on the model of its first decision for up to 24 hours (tier `pinned`); see [session pinning](/api-reference/route#session-pinning).

## Smart routing

**Smart routing** (under **Project Permissions**, on by default) is whether the router may pick the serving model at all. On is everything this page describes: tier escalation, the Small tier, task-group routes, record picks, session pins, and routing through a named model's anchored router. Turn it off and you only ever get responses from the model you select: a request that names a model is served exactly that model, and `auto` is served by the auto router's Medium model, deterministically (tier `fixed`). Your routers, records and recommendations stay intact for when you turn it back on.

## Automatic updates

Every routed call records the model that served it and how the task turned out, so Belvedir builds a per-task-group record of how each model actually performs on that kind of work. The **Routers** page shows each task group's observed success rate per model, that model's newest score in the task group's generated environment when one exists, and a recommendation: the cheapest model whose recorded results match the best one.

**Automatic updates** (under **Project Permissions**, on by default) decides what happens to that recommendation:

- **On**: for task groups you have not assigned a model to, Belvedir promotes the cheapest model whose recorded results match the best one, and machine-shaped requests in that task group serve it live (tier `group-record`). Conversation never routes this way, task groups with too few results keep their tier default, and a model you assigned yourself always wins over the record. Under the same toggle, a non-streaming request with a strict JSON output contract can be served by the Small tier first and escalated when the answer fails validation; the response reports which in `x-belvedir-cascade`.
- **Off**: nothing switches by itself. The router editor shows a **Recommended** band for each task group with its observed record, and an **Approve** button puts that one assignment into effect.

Your fine-tuned models earn traffic the same way, by winning on the record, once registered under **Cloud Inference**. The request and response contract, headers included, is on [chat completions](/api-reference/chat-completions).
