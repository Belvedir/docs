Agents don't need one model for everything. Keep a small local model for cheap, high-volume steps and a bigger hosted model for hard reasoning, and route each call to whichever fits. Both clients are instances of the same OpenAI class, so a single `instrumentModules: { openAI: openai.OpenAI }` covers them all:

```ts
import OpenAI from "openai";

const local = new OpenAI({
  baseURL: "http://127.0.0.1:11434/v1",
  apiKey: "ollama",
});
const hosted = new OpenAI({
  baseURL: "https://api.together.xyz/v1",
  apiKey: process.env.TOGETHER_API_KEY,
});

// route each step to the model that fits it
const { client, model } = needsDeepReasoning(step)
  ? { client: hosted, model: "Qwen/Qwen3-235B-A22B" }
  : { client: local, model: "qwen3:4b" };

const res = await client.chat.completions.create({ model, messages });
```

## Let Belvedir decide

You can write `needsDeepReasoning` yourself, or let Belvedir decide. Configure routing under the **Routing** page (a default model, an optional strong model for hard requests, and per-task-group overrides), then ask `POST /api/v1/route` before each call, authenticated with the same API key as ingest. A project can hold several routers, but exactly one is the **production** router: that is the config this endpoint serves. The others are drafts; stage a new setup there and click "Make production" to switch, instantly and reversibly. The decision is deterministic and fast: no model call, just your config plus a lexical match against your project's task groups and a complexity score on the request:

```ts
const res = await fetch("https://platform.belvedir.ai/api/v1/route", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "x-api-key": process.env.BELVEDIR_API_KEY,
  },
  // session_id is optional: pass your withSession/session id and the
  // session's first decision sticks, so a conversation stays on one model.
  body: JSON.stringify({ messages, session_id: sessionId }),
  // or { task: "summarize this doc" }
});
const route = await res.json();
// { configured: true, model: "qwen3:4b",
//   tier: "default" | "strong" | "group" | "pinned",
//   matched_group: { id, label } | null, complexity: 0.35, reason: "..." }

const model = route.configured ? route.model : "qwen3:4b"; // local fallback
const res2 = await client.chat.completions.create({ model, messages });
```

Every new project starts with a Default router (GLM 5.2 serves, clearly hard requests escalate to Claude Fable 5). Unconfigured projects (older ones, or those whose routers were deleted) get `configured: false` (never an error), so the call is safe to ship before the dashboard config exists. With `session_id` set, repeat calls in the same session return the first decision as `tier: "pinned"` for up to 24 hours; changing the routing config releases stale pins.

## Tune it from production data

Every span still records the model that served it, so Belvedir builds a per-group record of how each model actually performs on that kind of work. The Routing page shows each group's observed success rates per model, that model's newest score in the group's generated environment when one exists, and a one-click **auto-pick** recommendation: the cheapest model whose observed success rate is within a few points of the best. Apply it and save — the loop's fine-tuned specialists earn traffic the same way, by winning on the record.

Routing itself is a permission: **Smart routing** (Project Permissions, on by default) is whether the router may pick the serving model at all. Off means every request is served by exactly the model it names, and `auto` serves the router's Default model, deterministically.

With **Automatic updates** on (Project Permissions, the default), the record decides by itself: recognized task groups you haven't assigned a model to serve machine-shaped requests with the auto-pick winner live, as tier `group-record`, and requests with a strict JSON output contract can be served by the Small tier first with mechanical validation and automatic escalation. Turn it off and the record only recommends: the router editor lists each pending recommendation with its observed success rate, and an **Approve** button puts that one assignment into production. Details on the [router endpoint page](/api-reference/route).
