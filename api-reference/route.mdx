Asks which model should serve a call and executes nothing. Use it when your own code runs the model: local models, your own provider accounts, or a client you cannot repoint. The decision comes from the project's routers: size-tier defaults (Big for hard requests, Medium for the bulk, Small for quick machine tasks) plus per-task-group assignments. Belvedir matches the request to your task groups and scores the complexity of the instruction itself; pasted documents and payload text never escalate a request on size alone, though pasted code still counts as hard. The decision is fast and replayable: no LLM sits in the decision path, and the same input decides the same way. How tiers, task groups, **Smart routing** and **Automatic updates** work is on [Model Routing](/inference/mixture-of-models).

- **Authorization**: Bearer token with your API key, or use the `x-api-key` header.
- **Body**: `{ "messages": [...] }` or `{ "task": "summarize this doc" }`, plus an optional `"session_id"` (a body field on this endpoint, up to 200 characters) and an optional `"model"`: naming a model decides through that model's anchored router, exactly as naming it on [chat completions](/api-reference/chat-completions) does. Bodies cap at 128 KB.

```ts
const res = await fetch("https://platform.belvedir.ai/api/v1/route", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "x-api-key": process.env.BELVEDIR_API_KEY,
  },
  body: JSON.stringify({ messages, session_id: sessionId }),
});
const route = await res.json();
const model = route.configured ? route.model : "qwen3:4b"; // local fallback
```

## Response

```json
{
  "configured": true,
  "model": "qwen3:4b",
  "tier": "default",
  "matched_group": null,
  "complexity": 0.35,
  "reason": "...",
  "router_id": "...",
  "anchor_model": null
}
```

`tier` says why that model was chosen:

- `"group"`: a task group you assigned a model to matched.
- `"group-record"`: **Automatic updates** picked the model from the task group's recorded results.
- `"strong"`: the request scored as hard, so the Big model serves it.
- `"small"`: the request is a quick machine task (a short, single-shot instruction with a clear task shape and no code) and a Small model is set.
- `"pinned"`: an earlier decision for the same `session_id` was replayed (below).
- `"fixed"`: the project turned **Smart routing** off, so the named model (or the Default model, for `auto`) is served with no substitution.
- `"default"`: the Medium model.

`matched_group` is `{ id, label }` when a task group matched. `router_id` names the router that decided, and `anchor_model` is set when it is a router anchored on a model your code named. The cheaper tiers only ever serve machine-shaped tasks: calls that classify, extract, summarize, or demand a strict output format, template-style prompts, and tool loops. When a person is talking to the model (a dialogue, or a message with no task markers) the response comes from the top of the router; ambiguous requests count as conversation, so they route up, not down.

Every new project starts with a Default router, so a fresh project routes from day one; its contents are listed on [Model Routing](/inference/mixture-of-models). A project with no router (the auto router cannot be deleted, only replaced by making another router auto) gets `configured: false`, never an error, so the call is safe to ship before any dashboard config exists; keep a local fallback model.

## Session pinning

Pass your SDK session id as `session_id` and the session's first decision sticks: repeat calls return the same model as `tier: "pinned"` for up to 24 hours, keeping a conversation consistent and prompt caches warm. Changing a router releases stale pins (a pinned model no longer in the config is re-decided). Fresh decisions are logged, which is what powers the **Routers** page's observed per-task-group success rates and recommendations.

## Related endpoints

The endpoints below make the same decision and then run the call for you:
