An environment is a harness plus what's in the sandbox. Environments are distilled from your production traffic: each training set, once it has collected 50 or more **distinct** clean successful examples (near-duplicates are folded together), doubles as a reproducible setting you can train and evaluate against, with the examples defining what good output looks like for that kind of work. One in five of a training set's examples is held out for evaluation: training never uses those tasks, and the environment is built from nothing else, so a model is never scored on tasks it trained on. A training set right at the floor therefore yields an environment of about ten tasks; more traffic means a larger task set. The Environments page lists which of your training sets have crossed the floor and which are still collecting.

## Generated environments

On the Environments page, pick a harness and a training set, and the training set's held-out successful examples become the task list, one JSON object per line:

```json
{"task": "...", "expect": "..."}
```

where `task` is what the agent is asked to do and `expect` is the known-good outcome the judge grades against. Tasks can also carry an explicit verifier tag, which the bare form is shorthand for:

```json
{"task": "...", "verify": {"kind": "judge", "expect": "..."}}
```

The default driver is the first-party **Belvedir Runner**: a minimal agent loop (one model call per task) attempts each task, and a pinned independent judge grades whether the attempt accomplishes the task, treating `expect` as evidence of what success looks like rather than the only acceptable answer. A different approach or format than the reference still passes; empty or task-echoing attempts fail without a judge call. The judge is deliberately never the model under test (set `JUDGE_MODEL` to change it; the runner warns if you point it at the model under test), and swapping in your own agent per task is one variable: `BELVEDIR_HARNESS_CMD`, a shell command that receives the task on stdin and prints the attempt.

Only harnesses that accept a task list can back an environment: the Belvedir Runner, the agent scaffolds from the catalog (OpenClaw, Hermes, OpenCode, Prime Agent, Pi, QM, Mastra) or a repo of your own that reads the file at `BELVEDIR_TASKS_FILE` and handles that format.

### Synthesized verifiers

On hosted Belvedir, the wizard offers **Synthesize verifiers**: instead of grading every task against its recorded output alone, Belvedir writes a rubric per task — specific, checkable criteria distilled from the training set's own successes *and* failures — and the runner grades each criterion independently with partial credit. Rubrics only ship if they survive two gates: they must reproduce the outcomes of held-out examples the synthesis never saw (pass the recorded successes, fail the recorded failures), and no-effort attempts must not pass them. A synthesis that fails its gates falls back to the standard judge automatically, and the wizard tells you. Synthesis takes a few minutes and needs a training set slightly above the usual floor (the gate set is drawn from the training side of the split, on top of the 50 examples). Complete suites like SWE-bench bring their own tasks and are refused. The generated task set caps at 512 KB, and very long inputs or outputs are truncated per field so 50 tasks always fit; a training set whose examples are too long to be useful is refused with a clear message. Environment runs are ordinary benchmark runs: same sandbox, same pricing, same results contract. The Environments page can also run **simulations**: scripted episodes of an environment against an agent model you pick, without a full benchmark launch (`belvedir simulations run <simulation-id> --episodes 8` from the CLI).

## Run an environment under Harbor

Every environment exports as a [Harbor](https://harborframework.com) dataset, so you can run it on your own machine, against any Harbor agent, or feed it to a Harbor-compatible trainer:

```bash
belvedir environments export <project> --id <environment id> --out ./env
uv tool install harbor --with-editable /path/to/belvedir-platform/harbor   # the Belvedir agent, inside Harbor's own venv
export JUDGE_API_KEY=$OPENROUTER_API_KEY MODEL_API_KEY=$OPENROUTER_API_KEY
harbor run -p ./env -a oracle -y                                                   # validate the verifier: expect 1.0
harbor run -p ./env -a belvedir_harbor.agent:BelvedirAgent -m openai/gpt-4.1-mini -y   # score a model
harbor run -p ./env -a claude-code -m anthropic/claude-sonnet-4-5 -y                # or any Harbor agent
```

Each task becomes a directory: the prompt in `instruction.md` (with a line telling the agent to write its final answer to `/app/answer.md`), a `task.toml`, a tiny Dockerfile, and a verifier in `tests/`. Judge and rubric tasks are graded with the same independent judge the Belvedir Runner uses, against the recorded known-good answer or the synthesized rubric. Two deterministic verifier kinds are available for tasks you author: `code` runs the task's own `verify(answer, state)` function, and `state_diff` compares the files under `/app/state` to the task's golden files (a task's `setup.state` files are placed there before the agent runs). Those two run under Harbor only for now.

You can also run an environment through Harbor **from Belvedir**: pick **Belvedir Runner on Harbor** as the harness when generating it (or `--preset harbor-runner` from the CLI). Each task then runs in its own container, the run appears on My Benchmarks like any other, and the model calls are traced into your project. The task containers run on Modal: either Belvedir's Harbor workspace when the deployment provides one, or your own Modal account via `MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET` on the harness. To score a production agent that is a service rather than a model, set `BELVEDIR_AGENT_URL` (and optionally `BELVEDIR_AGENT_TOKEN`) on the harness: the runner posts each task as JSON and grades whatever your service returns. The judge's key is never in the export: `task.toml` references `JUDGE_API_KEY` from your environment, which is why `harbor run` asks to confirm host access (`-y` skips the prompt). `solution/solve.sh` writes the recorded answer so `-a oracle` checks the verifier before you spend on a model. Harbor imports a custom agent inside its own interpreter, so the Belvedir agent has to be installed there (the `--with-editable` above, or `PYTHONPATH=/path/to/harbor`); the oracle and Harbor's built-in agents need only Harbor itself. The Python package is not yet on PyPI. Rewards land in Harbor's jobs directory; Harbor prints the mean. Add `--limit 3` to the export for a smoke run.

## Use your own codebase as the harness

The best harness is **your own codebase**: pick one of the project's connected repos and the sandbox clones your real agent (private repos authenticate through your GitHub connection automatically; no token to paste), so the model is benchmarked in the exact harness it runs in production. Your repo needs a small entrypoint that reads the task file, runs each task through your agent, and writes `results.json` with a numeric `score`; the same automatic authentication applies to any harness whose repo is connected to the project.
