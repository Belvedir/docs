An environment is a harness plus what's in the sandbox. Environments are distilled from your production traffic — each group of similar tasks, once it has collected 50 or more clean successful examples, doubles as a reproducible setting you can train and evaluate against: the examples define what good output looks like for that kind of work. The Environments page lists which of your groups have crossed the floor and which are still collecting.

## Generated environments

On the Environments page, pick a harness and a group, and the group's successful examples become the task list — one JSON object per line:

```json
{"task": "...", "expect": "..."}
```

where `task` is what the agent is asked to do and `expect` is the known-good outcome the judge grades against. A harness of your own works as an environment as long as it reads the file at `BELVEDIR_TASKS_FILE` and handles that format. Environment runs are ordinary benchmark runs: same sandbox, same pricing, same results contract.

## Use your own codebase as the harness

The best harness is **your own codebase**: pick one of the project's connected repos and the sandbox clones your real agent (private repos authenticate through your GitHub connection automatically — no token to paste), so the model is benchmarked in the exact harness it runs in production. Your repo needs a small entrypoint that reads the task file, runs each task through your agent, and writes `results.json` with a numeric `score`; the same automatic authentication applies to any harness whose repo is connected to the project.
