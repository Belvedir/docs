An environment is a harness plus what's in the sandbox. Environments are distilled from your production traffic: each task group, once it has collected 50 or more **distinct** clean successful examples (near-duplicates are folded together), doubles as a reproducible setting you can train and evaluate against, with the examples defining what good output looks like for that kind of work. The environment is built only from the task group's held-out examples (the [one-in-five evaluation holdout](/training/overview#what-it-trains-on) that training never sees), so a model is never scored on tasks it trained on. A task group right at the floor therefore yields an environment of about ten tasks; environments need at least 5 held-out tasks, and more traffic means a larger task set. The Environments page lists which of your task groups have crossed the floor and which are still collecting.

## Generated environments

On the Environments page, pick a harness and a task group, and the task group's held-out successful examples become the task list, one JSON object per line:

```json
{"task": "...", "expect": "..."}
```

where `task` is what the agent is asked to do and `expect` is the known-good outcome the judge grades against. Tasks can also carry an explicit verifier tag, which the bare form is shorthand for:

```json
{"task": "...", "verify": {"kind": "judge", "expect": "..."}}
```

Generated environments are [Harbor](https://harborframework.com) datasets: the dataset is written when the environment is generated and refreshed at every run, so it always matches the task set, and `belvedir environments export` writes it to disk (see [Running on Harbor](#running-on-harbor)). The default driver is the first-party **Belvedir Runner**: a minimal agent loop (one model call per task) attempts each task, and a pinned independent judge grades whether the attempt accomplishes the task, treating `expect` as evidence of what success looks like rather than the only acceptable answer. A different approach or format than the reference still passes; empty or task-echoing attempts fail without a judge call. The judge is deliberately never the model under test (set `JUDGE_MODEL` to change it; the runner warns if you point it at the model under test).

The runner comes in two forms that share the loop and the judge. **Belvedir Runner on Harbor** runs each task in its own container and is preselected on hosted Belvedir. The in-sandbox **Belvedir Runner** runs the whole set in one Belvedir sandbox and needs no Modal account. Either is one click away in the wizard (`--preset harbor-runner` or `--preset belvedir` from the CLI; omit `--preset` for the default). To swap in your own agent per task, set `BELVEDIR_HARNESS_CMD`: a shell command that receives the task on stdin and prints the attempt.

Only harnesses that accept a task list can back an environment: the Belvedir Runner (on Harbor or in-sandbox), the agent scaffolds from the catalog that are available today (OpenClaw, OpenCode, Pi; the Hermes Agent, Prime Agent, QM, and Mastra cards are marked not yet available), or a repo of your own that reads the file at `BELVEDIR_TASKS_FILE` and handles that format.

## Synthesize verifiers

On hosted Belvedir, the wizard offers **Synthesize verifiers**. Instead of grading every task against its recorded output alone, Belvedir writes a rubric per task (specific, checkable criteria distilled from the task group's own successes and failures) and the runner grades each criterion independently with partial credit. Rubrics only ship if they reproduce the outcomes of held-out examples the synthesis never saw; a synthesis that fails that check falls back to the standard judge automatically, and the environment says so.

Synthesis runs in the background for several minutes (around ten on a full task group): the environment appears on the Environments page immediately, shows its progress, and gets its Run button once the verifiers land (`belvedir environments status <id> --wait` from the CLI). An environment whose synthesis is marked abandoned can simply be generated again. Synthesis needs a task group slightly above the usual 50-example floor. Complete suites like SWE-bench bring their own tasks and are refused. The generated task set caps at 512 KB, and very long inputs or outputs are truncated per field so 50 tasks always fit; a task group whose examples are too long to be useful is refused with a clear message. Environment runs are ordinary benchmark runs: same sandbox, same pricing, same results contract.

## Simulations

The Environments page can also run **simulations**: scripted episodes of an environment against an agent model you pick, without a full benchmark launch (`belvedir simulations run <simulation-id> --episodes 8` from the CLI). The agent model runs on Belvedir's account, so it must be a priced Claude, Grok, or hosted open model (see [Available models](/inference/models); `claude-opus-5` and `anthropic/claude-opus-5` spellings both work), and it follows the project's **Chinese models** setting; anything else is refused before the run starts.

## Running on Harbor

Every environment exports as a Harbor dataset, so you can run it on your own machine, against any Harbor agent, or feed it to a Harbor-compatible trainer:

```bash
belvedir environments export <project> --id <environment id> --out ./env
git clone https://github.com/Belvedir/harness-harbor      # ships the Belvedir agent as belvedir_harbor/
uv tool install "harbor[modal]"                            # Harbor itself, in its own venv
export PYTHONPATH=$PWD/harness-harbor                      # so Harbor can import belvedir_harbor
export JUDGE_API_KEY=$OPENROUTER_API_KEY MODEL_API_KEY=$OPENROUTER_API_KEY
harbor run -p ./env -a oracle -y                                                   # validate the verifier: expect 1.0
harbor run -p ./env -a belvedir_harbor.agent:BelvedirAgent -m openai/gpt-4.1-mini -y   # score a model
harbor run -p ./env -a claude-code -m anthropic/claude-sonnet-5 -y                  # or any Harbor agent
```

Each task becomes a directory: the prompt in `instruction.md` (with a line telling the agent to write its final answer to `/app/answer.md`), a `task.toml`, a tiny Dockerfile, and a verifier in `tests/`. Judge and rubric tasks are graded with the same independent judge the Belvedir Runner uses, against the recorded known-good answer or the synthesized rubric. Two deterministic verifier kinds are available for tasks you author: `code` runs the task's own `verify(answer, state)` function, and `state_diff` compares the files under `/app/state` to the task's golden files (a task's `setup.state` files are placed there before the agent runs). Those two run under Harbor only for now, and `state_diff` tasks need an agent that edits files in the container (OpenCode, Pi, Claude Code, and similar); the default Belvedir agent only writes an answer.

The judge's key is never in the export: `task.toml` references `JUDGE_API_KEY` from your environment, which is why `harbor run` asks to confirm host access (`-y` skips the prompt). `solution/solve.sh` writes the recorded answer so `-a oracle` checks the verifier before you spend on a model. Harbor imports a custom agent (`-a module:Class`) inside its own interpreter, so it has to be able to find `belvedir_harbor`: the public [`Belvedir/harness-harbor`](https://github.com/Belvedir/harness-harbor) repo vendors that package at its root, and pointing `PYTHONPATH` at the clone (above) is enough. The oracle and Harbor's built-in agents need only Harbor itself. The `belvedir-harbor` package is not yet on PyPI, so there is no `pip install` for it. Rewards land in Harbor's jobs directory; Harbor prints the mean. Add `--limit 3` to the export for a smoke run.

### From Belvedir

You can also run an environment through Harbor from Belvedir: pick **Belvedir Runner on Harbor** as the harness when generating it (preselected on hosted Belvedir; `--preset harbor-runner` from the CLI). Each task runs in its own container, the run appears on My Benchmarks like any other, and the model calls are traced into your project. To score a production agent that is a service rather than a model, set `BELVEDIR_AGENT_URL` (and optionally `BELVEDIR_AGENT_TOKEN`) on the harness: the runner posts each task as JSON and grades whatever your service returns.

### Managed workspace or your own Modal account

The task containers run in one of two places, and the same applies to the Harbor-format suites on the [Benchmarks](/benchmarks/overview) page:

- **Belvedir's managed workspace** is the default on hosted Belvedir: leave `MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET` blank on the harness. Managed runs execute a pinned version of the catalog's Harbor driver, so the harness must keep the driver's install and run commands unchanged, and its env may only carry the variables the driver reads (`MODEL`, `MODEL_API_BASE`, `MODEL_API_KEY`, `MODEL_LABEL`, `JUDGE_MODEL`, `JUDGE_API_BASE`, `JUDGE_API_KEY`, `HARBOR_DATASET`, `HARBOR_AGENT`, `HARBOR_N_TASKS`, `HARBOR_CONCURRENCY`, `HARBOR_TASK_NAMES`, `HARBOR_MODEL`, `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET`, `BELVEDIR_AGENT_URL`, `BELVEDIR_AGENT_TOKEN`, `OPENROUTER_API_KEY`). `HARBOR_AGENT` must be a plain Harbor agent name (`terminus-2`, `claude-code`, `belvedir`; not a `module:Class` import path), `HARBOR_CONCURRENCY` is 1 to 4, `HARBOR_N_TASKS` is blank or 1 to 50, the harness uses CPU compute, and your organization must have credits or pay as you go on. A launch that fails one of these conditions is refused with a message naming the variable or condition.
- **Your own Modal account**: set `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` on the harness (`--env` from the CLI) and the same harness runs there, with none of the managed-workspace limits and any edits to the driver you like.

## Use your own codebase as the harness

The best harness is **your own codebase**: pick one of the project's connected repos and the sandbox clones your real agent (private repos authenticate through your GitHub connection automatically; no token to paste), so the model is benchmarked in the exact harness it runs in production. Your repo needs a small entrypoint that reads the task file, runs each task through your agent, and writes `results.json` with a numeric `score`; the same automatic authentication applies to any harness whose repo is connected to the project. Connect repos under **Project settings → Repository access**.
